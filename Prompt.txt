Je travaille sur un projet intitulé Smart Campus – CampusServices, plus précisément la brique Gestion des Services du Campus.
Le backend du projet est déjà préparé. Je veux maintenant créer un frontend complet, clair, moderne et fonctionnel qui communique avec ce backend.

Le frontend doit représenter une plateforme universitaire permettant aux étudiants d’utiliser plusieurs services du campus depuis une seule interface.

Le module couvre trois grands services :

Gestion de la bibliothèque
Réservation de salles de travail
Gestion des demandes administratives

Le système doit être utilisé par plusieurs types d’acteurs :

Étudiant
Administrateur
Bibliothécaire

Il existe aussi un système externe appelé EnrollSys, utilisé côté backend pour vérifier si un étudiant est valide avant qu’il puisse utiliser les services.

1. Objectif général du frontend

Créer une interface web pour le système CampusServices.

L’interface doit permettre aux étudiants de :

consulter les livres disponibles dans la bibliothèque ;
emprunter un livre ;
retourner un livre emprunté ;
consulter les salles disponibles ;
réserver une salle de travail ;
annuler une réservation ;
soumettre une demande administrative ;
consulter l’état de ses demandes.

L’interface doit permettre à l’administrateur de :

consulter les demandes administratives reçues ;
valider ou refuser une demande ;
ajouter un motif de refus ;
gérer la disponibilité des salles.

L’interface doit permettre au bibliothécaire de :

consulter le catalogue de livres ;
ajouter, modifier ou supprimer un livre ;
enregistrer les emprunts ;
enregistrer les retours ;
voir l’état de disponibilité des livres.
2. Style général demandé

Le frontend doit être :

moderne ;
simple à utiliser ;
responsive ;
adapté aux étudiants et au personnel universitaire ;
clair, avec une navigation facile ;
structuré avec des pages séparées selon les fonctionnalités.

L’interface doit avoir un design de type dashboard universitaire.

Utiliser une organisation propre avec :

une barre latérale ou un menu de navigation ;
une page d’accueil ;
des cartes statistiques ;
des tableaux de données ;
des formulaires propres ;
des boutons d’action visibles ;

5. Module Bibliothèque côté Étudiant

Créer une page Bibliothèque.

Cette page doit afficher le catalogue des livres sous forme de tableau ou de cartes.

Chaque livre doit afficher :

titre du livre ;
auteur ;
disponibilité : Disponible ou Emprunté ;
date de retour prévue si le livre est déjà emprunté ;
bouton “Emprunter” si le livre est disponible.

Fonctionnalités attendues :

rechercher un livre par titre ;
filtrer les livres par disponibilité ;
consulter la liste des livres ;
emprunter un livre disponible.

Quand l’étudiant clique sur Emprunter :

afficher une confirmation ;
envoyer la demande au backend ;
si l’étudiant est valide et que le livre est disponible, afficher un message de succès ;
mettre à jour l’état du livre en “Emprunté” ;
afficher la date de retour prévue.

Prévoir les erreurs suivantes :

livre non disponible ;
étudiant non valide ;
nombre maximum de livres atteint ;
erreur serveur.

Règle métier importante :

un étudiant ne peut pas emprunter plus de 3 livres simultanément ;
un livre ne peut être emprunté que s’il est disponible.

7. Module Réservation de salles côté Étudiant

Créer une page Réservation de salles.

Cette page doit afficher les salles disponibles avec :

L’étudiant doit pouvoir :

Processus de réservation :

l’étudiant consulte les salles disponibles ;
il choisit une salle ;
il choisit un créneau libre ;
il confirme la réservation ;
le frontend envoie la demande au backend ;
si le créneau est disponible, afficher un message de succès ;

Prévoir les erreurs suivantes :

étudiant non valide ;
étudiant possède déjà une réservation au même créneau ;
erreur serveur.

Règles métier importantes :

une salle ne peut être réservée que sur un créneau libre ;
un étudiant ne peut pas avoir deux réservations au même créneau ;
seul l’administrateur peut gérer la disponibilité des salles.

18. Contraintes importantes

Le frontend doit respecter ces règles :

Un étudiant non valide ne peut accéder à aucun service.
Un livre ne peut être emprunté que s’il est disponible.
Un étudiant ne peut pas avoir plus de 3 livres empruntés en même temps.
Une salle ne peut être réservée que sur un créneau libre.
Un étudiant ne peut pas avoir deux réservations au même créneau.
Une demande administrative doit obligatoirement avoir un type, une date de soumission et un identifiant étudiant.
Une demande administrative peut passer de “En attente” vers “Validée” ou “Refusée”.
La disponibilité des salles est gérée uniquement par l’administrateur.

21. Communication avec le backend

Préparer un fichier api.js pour centraliser les appels API.

Exemple de routes possibles à adapter selon le backend :

POST /auth/login

GET /books
POST /books
PUT /books/:id
DELETE /books/:id
POST /books/:id/borrow
POST /books/:id/return

GET /rooms
POST /rooms
PUT /rooms/:id
DELETE /rooms/:id
POST /rooms/:id/reserve
DELETE /reservations/:id

GET /requests
POST /requests
PUT /requests/:id/validate
PUT /requests/:id/refuse

GET /students/:id/status

Le frontend doit être préparé pour recevoir les données depuis le backend, pas seulement utiliser des données statiques.
